## 一、功能基线（已实现）

### REQ-001 首次配置流程

- 优先级：P0
- 状态：已实现
- 需求：无管理员时打开服务直接进入配置页，三步完成：管理员（用户名 + 主密码）、绑定 TOTP、存储与推送。不生成、不校验初始化码。
- 验收：全新安装打开首页进入配置页；三步可完成；完成后自动切 HTTPS 并给出 Dashboard 地址。

---

### REQ-002 单管理员登录与会话

- 优先级：P0
- 状态：已实现
- 需求：用户名 + 主密码 + TOTP 三要素登录；刷新不掉线；退出登录立即失效；失败按 IP 限流。
- 验收：缺任一要素均登录失败；连续失败触发 429；退出后需重新登录。
- 演进：「会话 1 小时」与「手动锁定」已被 **REQ-152**（v1.3.3）取代——绝对过期整条删除，改为双档滑动空闲；「锁定」并入「退出登录」。本节保留原验收口径，只把措辞对齐现状。

---

### REQ-003 owner 门禁与旧数据接管

- 优先级：P0
- 状态：已实现
- 需求：是否「已初始化」以管理员是否存在为准，不以 vault 文件是否存在为准；已有管理员时 `/setup` 返回 410；旧 vault 无管理员时先备份为 `vault.enc.bak` 再写入新管理员。
- 验收：半初始化、遗留 vault、重装后均能回到配置页并完成认领，不出现「已初始化」死锁。

---

### REQ-004 持久 CA 与证书复用

- 优先级：P0
- 状态：已实现
- 需求：首次安装生成根 CA 并持久保存（与用户数据分离）；升级、普通重装不更换 CA；服务器证书随用户数据清理，下次配置用同一 CA 重签。
- 验收：升级后浏览器不再提示新根证书；`/api/tls/status` 可查 CA 指纹与 SAN。

---

### REQ-005 审批工作台

- 优先级：P0
- 状态：已实现
- 需求：待审批在上、历史在下，用分隔线与小标题区分；服务环境变量授权并入同一工作台；拒绝需填原因；历史只读可清空。
- 验收：待审批卡片可同意/拒绝；拒绝原因入库；历史与待审批不混排。

---

### REQ-006 凭证管理与连接测试

- 优先级：P0
- 状态：已实现
- 需求：支持 PostgreSQL / SSH / 账号类凭证；表单内「测试连接」，服务端 5 秒超时，返回成功与耗时或失败原因；测试不落盘、不写密钥日志。
- 验收：错误参数能显示失败原因；正确参数显示耗时；审计记录不含密码或私钥。

---

### REQ-007 凭证密钥查看

## 二、本轮待开发

### REQ-101 独立登录页与路由拆分

- 优先级：P0
- 状态：已联调
- 需求：新增 `/login` 独立页面；未登录访问 `/dashboard` 302 至 `/login`；登录表单从 dashboard 内嵌遮罩中移出，遮罩只用于会话中途手动锁定。
- 验收：未登录访问 `/dashboard` 返回 302；`/login` 直接 200；锁定后跳转登录页。
- 实现：`templates/login.html` + `dashboard.login_page()`；`do_GET` 先规范化路径（去 query）再判 `/login`，路径顺序 login → dashboard；遮罩整段删除（原方案「保留精简遮罩」在实现时修订，理由见 PRD-101 4.3）；selftest [50] 覆盖 302 门禁与已登录回跳。

### REQ-102 登录页 TOTP 六格输入与自动提交

- 优先级：P0
- 状态：已联调
- 需求：验证码为 6 个单字符输入框；输入自动跳格、退格回上一格、粘贴 6 位自动铺满；填满 6 位自动提交登录；「登录」按钮保留，可手动点击。
- 验收：粘贴 6 位即触发登录；按钮点击同样生效；未填满不发送请求。
- 实现：`#t0`～`#t5` 六格，`input` 事件逐格跳转、`keydown` 处理 Backspace 与左右方向键、容器 `paste` 事件铺满；`code().length === 6` 即 `submitLogin()`；`busy` 标志在请求期间禁用按钮与六格，防双发；仅第 1 格 `autocomplete="one-time-code"`。

### REQ-109 systemd 下 CA 目录只读导致首次初始化失败

- 状态：已联调（`ReadWritePaths` 放行 CA 目录 + 启动补签；8.4/8.7 两次初始化均成功）

- 现象：浏览器侧只是 `Failed to fetch`，服务端 journal 里是真异常：

  ```text
  OSError: [Errno 30] Read-only file system: '/var/lib/agentkeyguard-ca/ca.crt'
  ```

- 根因：`config.CA_DIR` 默认 `/var/lib/agentkeyguard-ca`，而 `debian/agentkeyguard.service.in` 里
  `ProtectSystem=strict` 只放行了 `ReadWritePaths=/var/lib/agentkeyguard`，CA 目录不在白名单内。
  `config.py` 第 64 行已经为 `TLS_DIR` 记录过同样的教训（"systemd ProtectSystem=strict 下 /etc 只读"），
  但 `CA_DIR` 被漏在外面。
- 连带后果（比报错本身更麻烦）：
  1. `setup.finish()` 先落 `vault.enc` 与 `master.key`，再签发证书，异常发生在中间 → 留下**半初始化状态**；
  2. `mark_owner()` 没执行，`has_admin()` 仍为 false，`/setup` 可以重进；
  3. 但 CA 目录为空 → 没有 HTTPS 证书 → 所有 `/api/*` 返回 `403 https_required` → **连登录都不可能**，只能清空数据目录重来；
  4. 重启后 `ensure_owner_state()` 会把已有 vault 判定为已初始化，`/setup` 变成 410，卡死。
- 需求：
  - 修复 unit：`ReadWritePaths=/var/lib/agentkeyguard /var/lib/agentkeyguard-ca`（或把 CA 放回 `DATA_DIR` 下的子目录）；
  - `finish()` 改为**先完成不可逆部分的前置校验**：先确保 CA 能签发，再落 vault/master.key；任一步失败要回滚，不留下半初始化状态；
  - 启动时若检测到「有 vault 但无证书」，应自动补签发证书，而不是卡在 410。
- 验收：全新安装（systemd 启动）三步 setup 一次通过；人为把 CA 目录设为不可写时，setup 明确报错且**不产生** `vault.enc`/`master.key`；selftest 增加一条「CA 目录不可写时 finish 回滚」的用例。

### REQ-112 手机端无法访问（Public Base / 证书 SAN / 域名方案）

- 优先级：P0
- 状态：已联调（**方案收敛为纯 IP 访问**：手机用 IP + 装根证书即可，域名与 DNS 重写方案放弃）
- 来源：2026-10-29 联调。iPhone 上即便已把根证书装进受信任列表，仍打不开 `https://127.0.0.1:7700/dashboard`（用户原话：「这一步体验为 0 分」）。
- 根因分三层，任何一层单独存在都会导致失败：
  1. **`127.0.0.1` 在手机上指向手机自己**，不可能连到 WSL 里的服务。而 `Public Base` 默认值正是 `http://127.0.0.1:7700`；
  2. **证书 SAN 不含局域网 IP**。实测签发出的 SAN 是 `IP:127.0.0.1, IP:127.0.0.1, DNS:example.akg.arpa, DNS:localhost`，用 `https://192.0.2.12:7700` 访问必然证书不匹配。
     根因比"漏了 IP"更细：`setup.finish()` 传给 `issue_server_cert` 的 IP 来自 `server._ip()`，即 **TCP 对端（客户端来源）IP**，不是本机 IP。从 Windows 浏览器经 WSL 端口转发进来，来源 IP 就是 `127.0.0.1`，于是 `[ip, "127.0.0.1"]` 里的两个值相同，证书里一个局域网地址都没有。`network.local_ip()` 明明能取到本机局域网 IP，却没被用上。**证书内容取决于"谁在配置"，这是设计缺陷**；
  3. **`example.akg.arpa` 属于 `.arpa` 保留域**（反向 DNS 专用），公网 DNS 永远不解析，手机也无法像电脑那样改 hosts，等于不可用。
- 连带影响：审批推送（Bark）里的审批链接由 `Public Base` 拼接，`Public Base` 是 `127.0.0.1` 时**手机点开必然打不开**，审批流整体失效——这是本项目最核心的链路。
- 需求：
  - 首次配置必须**引导并校验**「手机可访问地址」：填局域网 IP 或真实域名，禁止默认提交 `127.0.0.1` / `localhost`；
  - 证书 SAN 必须覆盖该地址（IP 或 DNS），并去重；
  - 域名方案（`*.akg.arpa`）需要明确的前置条件说明：手机必须能解析该域名（内网 DNS 或自建解析），否则改用 IP；
  - 配置完成后给出一次「手机打开此链接试试」的验证入口或自检。
- 验收：电脑与手机处于同一局域网，手机打开审批链接能完成一次审批，全程无证书告警、无 DNS 失败。
- 实施后追加发现（2026-10-29 深夜，v1.1.2 已发但未解决）：本机的 WSL 处于
  **mirrored 网络模式**（`eth0` 直接拿到宿主机局域网地址 `192.0.2.12`，网关 `192.0.2.1`）。
  实测 **Windows 宿主机访问 `http://192.0.2.12:7700` 超时（curl 返回 000），
  访问 `http://127.0.0.1:7700` 正常 200**；同一时刻 WSL 内部访问两个地址都是 200。
  也就是说 v1.1.2 里的「自动探测」默认值 `network.local_ip()` 在 mirrored 模式下
  指向的是**宿主机自己的网卡**，从宿主机与手机都不一定能连到 WSL 内的监听 → 见 REQ-114。

### REQ-114 Public Base 默认值应取「配置者实际访问的 Host」，不要猜 IP

- 优先级：P1
- 状态：已联调（三级取值实测：手动 → 请求 Host → 探测；配合纯 IP 方案）
- 来源：2026-10-29 深夜。v1.1.2 已把 `Public Base` 默认值改成 `network.local_ip()`，
  但本机 WSL 是 mirrored 模式：`network.local_ip()` 返回 `192.0.2.12`，
  而这个地址从 Windows 宿主机访问是**超时**的（`curl.exe` 返回 000），
  只有 `127.0.0.1` 能通。用户实际看到的报错就是「无法访问此页面，响应时间太长」。
- 根因：`network.local_ip()` 用 UDP connect 到 8.8.8.8 取出口地址，拿到的是
  **宿主机网卡地址**，而监听在 WSL 的网络命名空间里。mirrored 模式下两者同名不同栈，
  宿主机访问自己的 LAN IP 不会环回进 WSL；NAT 模式下则相反（WSL 拿到 172.x，宿主机可以直连）。
  两种模式下"猜一个 IP"都不可能永远正确。
- 需求（2026-10-29 二次澄清：地址是**动态**的，不能只做一次性快照）：
  1. **默认值**：首次配置时取**浏览器地址栏的 Host**（用户此刻真正能连通的那个），服务端不猜 IP。
  2. **可手动覆盖**：包括 Skill 地址在内的所有对外地址，用户都能在设置里改；
     改完立即生效，并同步重签证书（REQ-112 已有换发逻辑）。
  3. **自动跟随**：本机地址可能变（DHCP 续租、WSL 重启换网段、拔插网线切换有线/无线），
     服务应能感知并给出提示，而不是继续用旧地址；至少做到启动时重新探测一次，
     并在设置页展示「当前探测到的地址」与「当前生效地址」两个值，便于用户判断是否已过期。
  4. **回环 vs DHCP**：监听是 `0.0.0.0`（同时覆盖回环与 DHCP 地址），但**对外宣称的地址**
     必须是对方能回连的那个。WSL 里 `127.0.0.1` 只对宿主机有效、`192.168.x.x` 只对局域网有效，
     两者不能互相替代，所以必须允许用户按使用场景自己选。
  5. **可达性自检**：填入后服务端回连自己（或前端点「测试」），不通就给出具体原因
     （端口未放行 / 防火墙 / mirrored 模式 / 地址属于其他网段）。
  6. 设置页列出本机所有网卡地址，并标注哪些是 WSL / docker 虚拟网卡，
     避免用户把 `172.17.0.1` 当成局域网地址填进去。
- 补充记录（2026-10-29 实测）：用户在「Agent 接入」点开 MD 文档打不开，
  根因与本条相同（Skill 链接用的是 `192.0.2.12`）；改成 `127.0.0.1` 后立即正常，
  进一步印证「地址必须可手动改、且默认值要取用户实际访问的 Host」。
- 验收：在新装 WSL（mirrored 模式）上走完初始化，页面给出的地址**在宿主机浏览器里能直接打开**；
  手机与电脑同局域网时，同一地址在手机上也能打开；填错地址时有明确中文提示而不是超时。
- 2026-10-30 修正：`_public_base()` 此前把回环地址当「没配置」直接跳过，主人填了
  `https://127.0.0.1:7700` 仍被替换成局域网 IP。现在**显式配置一律采信（含回环）**；
  手机可达性改由 `approval.push_base()` 单独兜底——配置是回环时，审批链接回退局域网 IP。
  自检 [62] 固化这条。注意与 REQ-112 的「首次配置禁止回环」不冲突：那条约束的是 setup 向导，
  设置页允许回环，供本机 Agent 使用。

### REQ-113 TLS 握手请求客户端证书，浏览器弹「选择用于身份验证的证书」

- 优先级：P0
- 状态：已联调（8.7 HTTPS 访问不弹选择框；`tls_context` 固定 `CERT_NONE`）
- 来源：2026-10-29 联调。重新加载页面后，Windows / Chrome 弹出「选择用于身份验证的证书」，里面列了 `MS-Organization-Access`、`Microsoft Your Phone` 等一堆系统证书，用户不知道选哪个；点「取消」才能正常访问。
- 根因：服务端 TLS 上下文默认索要客户端证书，但 mTLS 在本项目里是**明确关闭**的：

  ```python
  # tls.py:291
  def tls_context(cert_file, key_file, ca_file, verify_mode: int = ssl.CERT_OPTIONAL)
  # cli.py:262  未覆盖该参数
  ssl_ctx = tls.tls_context(cert_f, key_f, ca_f) if tls_on else None
  ```

  `CERT_OPTIONAL` 会让服务端在握手中发送 CertificateRequest，浏览器/操作系统随即要求用户挑一张客户端证书。实测 `openssl s_client -state` 输出 `SSLv3/TLS write client certificate` 可复现。
  与 `devices.py` 的「mTLS 保留但不启用」、`setup.finish()` 里 `"mtls_mode": "off"` 自相矛盾。
- 影响：每次首次访问都可能弹窗；**选中一张非本 CA 签发的证书会导致握手失败**，用户会误以为是站点坏了；点取消才能进，但没人知道要取消。
- 决策：**本项目不需要 mTLS**（见 REQ-303），因此本条不是"把 verify_mode 改成可选"，而是**彻底移除客户端证书请求**。
- 需求：
  - `tls.tls_context()` 固定 `verify_mode = ssl.CERT_NONE`，并删除 `verify_mode` 参数，从签名上就不允许再传；
  - 删除 `ctx.load_verify_locations(ca_file)` 这类为校验客户端证书而加载的信任链（服务端不需要验证客户端）；
  - 清理 `devices.py` 与 `/api/devices*`、`bootstrap_context` 里与客户端证书相关的残留（与 REQ-012、REQ-303 合并处理）；
  - selftest 增加一条：握手响应中不应出现 CertificateRequest。
- 验收：`openssl s_client -state` 输出中不再出现 `write client certificate`；浏览器访问 `https://<host>:7700` 全程无证书选择框。

### REQ-118 环境变量录入（自动识别 + 键值对列表 + 提交前校验）

- 优先级：P1
- 状态：待联调（暂无实际项目可验，延后到有真实 `.env` 时再走一遍）
- 来源：2026-10-29 联调。用户整段粘贴 `AGENTKEYGUARD_ENV_URL=https://…` 后追问：
  「我的 URL 和等于号之间并没有填空格，不知道会不会影响注入……最好是采用一种新的填入变量的方式，
  整段粘贴确实方便，但它缺少对等号中间有没有空格的考虑」。
- 实测结论（现版本 `dashboard.html` 第 630-637 行）：

  ```js
  for (const line of $('svcEnv').value.split('\n').map(x => x.trim()).filter(Boolean)) {
    const i = line.indexOf('=');
    if (i <= 0) throw new Error('环境变量格式：KEY=value');
    env[line.slice(0, i).trim()] = line.slice(i + 1);   // ← 值没有 trim
  }
  ```

  行首尾会被 `trim()`，但**等号右侧原样保留**。所以：
  - `KEY=value` ✅ 正常；
  - `KEY= value` ❌ 值变成 `" value"`（带前导空格），URL 这类值直接失效；
  - `KEY =value` ✅ key 被 trim，仍可用；
  - 这个不对称行为非常反直觉，用户凭直觉写「等号两边加空格」就会踩雷。
- 需求：
  0. **录入方式 = 两种入口，同一套结果**：
     - 整段粘贴：像填快递收件地址那样一次贴进去；
     - 逐条手填：变量名一个框、值一个框，点「+」加一行。
     两者最终都落到**同一份键值对列表**（一行一个 key/value），列表里每行都能单独编辑、删除，
     底部还有「+ 添加一行」。用户说的是「你觉得添加少了或者多了，可以添加和删除」。
  0b. **不要求格式，自动识别**（用户原话：「最好是能做到不要求格式，自动识别变量」）：
     - 识别依据：**变量名肯定是全大写**（`[A-Z][A-Z0-9_]*`），这是最可靠的分隔信号；
     - 分隔符不管：`=` / `:` / 空白 / 制表符 都认；
     - 值**前后不保留空格**（用户明确要求），中间空格原样保留；
     - 若确实去掉了空白，在该行给一个可展开的小提示「第 3 行值首尾各有 1 个空格，已去除」，
       点一下可以撤销 —— 既满足「自动识别」，又不会静默吞掉可能有意义的内容；
     - 识别不出来的行**不静默丢弃**，收进「未识别内容」区并高亮，让用户决定改还是删；
     - 识别完成后先渲染成键值对列表，用户确认/微调后再点「注入」，不直接提交原始文本。
     - 兜底规则：若整段里**一个键值对都没识别出来**，再退回宽松规则（任意 `KEY=VALUE`，key 允许小写），
       免得用户的小写变量名全军覆没；
     - 明确不支持的形态（多行值、PEM 私钥、带换行的 JSON）进「未识别内容」区并提示改用逐条填写。
  1. **解析容错**：`KEY = VALUE`、`KEY= VALUE`、`KEY =VALUE` 三种写法都必须等价；
     额外支持 `export KEY=VALUE` 前缀、CRLF 行尾、`#` 开头的注释行、值里含 `=`
     （按第一个 `=` 切分，现有实现已满足）、值用引号包裹（`KEY="a b"` 去掉外层引号）。
  2. **不要静默 trim 值**：值的前导/尾随空格可能是有意义的（base64、带空格的 key），
     但必须在预览里**显式标出**「该值首尾含空白」让用户自己决定。
  3. **粘贴后先预览再创建**：整段粘贴 → 解析成表格（变量名 / 值 / 异常标记）→ 用户确认后才创建服务。
     错误行高亮并指出原因，不要一句 `环境变量格式：KEY=value` 打发。
  4. 同时接受 **JSON 对象**与 **.env 文本**两种粘贴格式，自动识别。
  5. **校验前置**：变量名必须匹配 `^[A-Za-z_][A-Za-z0-9_]{0,63}$`；重复名当场报错并高亮那一行；
     空值、纯空白、超长值给出提示；**在提交前就把格式问题挡掉**，不要等服务创建完才在注入时报错。
  6. 变量名的大小写敏感、值里的 `=` 与 `#` 原样保留，不做转义也不做截断。
- 验收：逐条添加能正确生成；粘贴 `KEY= value`、`KEY = value`、`export KEY=value`、带注释的 .env
  四种写法解析结果一致；重复变量名在提交前报错；预览里能看到可疑空白；
  创建后注入到容器的值与预期逐字节一致。

  2. 用户发现直接访问 `https://example.akg.arpa:7700/` 是 404，必须手打 `/dashboard`。
- 事实澄清（写进文档，避免以后重复讨论）：
  - **DNS 记录做不到指定端口和路径**。A / AAAA / CNAME 只解决「名字 → 地址」，
    协议里没有端口和 path 字段；浏览器不写端口就只会试 443（https）/ 80（http）。
  - 想让「只敲域名」可用，只有三条路：
    a. 服务直接监听 443（需要 `CAP_NET_BIND_SERVICE` 或 root）；
    b. 在前面挂反向代理（Caddy / Nginx）监听 443，转发到 7700；
    c. 在网关侧做端口转发 443 → 7700。
- 需求：
  1. **补根路径路由**：`GET /` 已登录 → 302 `/dashboard`；未登录 → 302 `/login`；
     初始化前 → 302 `/setup`。当前 `/` 直接 404（`server.py` 里根本没有 `/` 的分支）。
  2. 设置页新增「访问方式」说明：当前是 `https://<域名>:7700`，
     若想免端口访问需要绑定 443 或挂反代，并给出两种做法的简短指引（不绑定具体产品）。
  3. 完成页/登录页展示的地址统一带上端口，不给出会 404 的裸域名。
- 验收：浏览器输入 `https://example.akg.arpa:7700`（无路径）能直接到登录页或控制台，不再 404。

### REQ-125 网络与域名体验：分层地址 + mDNS + 部署形态引导

- 优先级：P1
- 状态：部分完成（分层地址 + 虚拟网卡标注已做；mDNS 放弃，域名方案按 REQ-140 保留继续做）
- 来源：2026-10-29 联调后期。用户原话：
  「因为是在 WSL 里面运行的，所以我不得不使用 127.0.0.1 来做 DNS 重写，这样才能在电脑上访问；
  如果手机访问，我还得给它切换回 192.0.2.12……本地如果是单设备部署，只能在 WSL 里部署，
  那只能通过 NAT 的方式，不然镜像模式下手机上无法访问。
  这个网络这一块怎么路由、怎样获得更好的体验，我需要你的建议和支持，但这个体验改进一定要记录下来。」
- 问题拆解（三类地址各自只对一类客户端有效，产品目前混在一起宣传）：

  | 地址 | 谁能访问 | 典型用途 |
  | --- | --- | --- |
  | `127.0.0.1`（回环） | 只有**跑服务的那台机器**（WSL 里靠宿主的 localhost 转发） | 本机调试、装根证书 |
  | `192.168.x.x`（局域网 IP） | 同网段的其他设备 | 手机审批、其他电脑 |
  | `<name>.akg.arpa`（域名） | 取决于 DNS 指向谁 | WebAuthn 的 RP ID 必须是域名 |

  WSL 的 mirrored 模式下，WSL 与宿主机共用同一个 LAN IP，宿主机访问自己的 LAN IP 又不环回，
  于是「同一台机器上，本机能通的地址手机必然不通，手机能通的地址本机必然超时」——
  用户被迫在 AdGuard 里反复改重写规则。
- 需求：
  1. **地址清单（照抄 AdGuard Home 的做法）**：配置完成后给出一张「访问地址」清单，
     IPv4 / IPv6 / localhost / mDNS 名 **全部列出来**，每条标注「本机能用 / 手机能用 / 需要什么前置条件」，
     用户挑一条一定能通的即可，而不是只给一个地址让他自己撞墙。
     审批链接与二维码一律用**局域网地址**，本机测试入口用**本机地址**。
  2. **部署形态识别**：首次配置时判断是真机 / WSL / 容器，按形态给出对应的网络说明；
     检测到 WSL + mirrored 模式时明确提示：「本机可用 127.0.0.1，手机不可用；要手机可访问请改用
     NAT 模式 + 端口转发，或在真机上部署」，并直接给出现成命令。
  3. **可选 mDNS 广播**：内置 `<hostname>.local` 的 mDNS 应答（类似 Home Assistant 的做法），
     开关默认关闭；开启后 iOS / Android / macOS 无需任何 DNS 配置即可访问，Windows 需 Bonjour。
  4. **`.localhost` 别名**：浏览器按 RFC 6761 强制把 `*.localhost` 解析到回环，
     提供 `https://<name>.localhost:7700` 作为本机访问的固定入口，且该域名可合法作为 WebAuthn 的 RP ID，
     本机测生物识别时不必改任何 DNS。
  5. **DNS 引导分级**（按覆盖面排序，见 REQ-122 的通用文案要求）：
     路由器 DHCP 下发内网 DNS（全家生效，一次配置）> 单机 hosts（只本机）> 手动指定 DNS。
     每级标注「影响范围 / 配置难度 / 是否需要重启网卡」。
- 验收：WSL 场景下面板明确写「手机暂时不可达」并给出两条修复路径；真机场景默认给出局域网地址且手机可直接打开；
  打开 mDNS 后手机不改任何 DNS 即可用 `<hostname>.local` 访问；本机用 `<name>.localhost` 可直接完成一次
  生物识别绑定。
- **mDNS 可行性实测（2026-10-29，WSL 环境）**：
  - 库：Debian 源里有 `python3-zeroconf 0.147.0`，可直接加进 requirements，无编译依赖；
  - 广播：在 WSL 里注册 `akg-probe.local → 192.0.2.12:7700`，**WSL 内部可立即解析到**，
    说明 mirrored 模式下多播能正常发出；
  - **Windows 解析失败**：`ping akg-probe.local` 与 `Resolve-DnsName` 都返回「找不到主机」，
    `curl http://akg-probe.local:7700` 返回 000。原因：Windows 的 DNS 客户端**不内置 mDNS 解析器**，
    需要额外安装 Bonjour（iTunes / Bonjour Print Services）才会走 5353 组播；
  - 结论：**mDNS 的定位应是「手机零配置入口」**（iOS / Android / macOS 原生支持），
    Windows 侧继续用 IP、`.localhost` 或 hosts。若强行要求 Windows 也能用，需在文案里说明「需安装 Bonjour」；
  - 另外两条实现约束：
    1. Docker 默认 bridge 网络**不通多播**，容器部署必须 `--network host` 才能广播 mDNS；
    2. `zeroconf` 遇到重名会自动改成 `akg-probe-2.local`，对产品不友好 ——
       需要固定 `<hostname>.local` 并在冲突时明确提示用户，而不是静默改名。

- **与既有设计冲突，需明确变更**：REQ-107 与设置页现有文案都写着「token 不存服务器，Agent 从本机读取」。
  本需求改为 **token 加密存入 vault**，理由是 Agent 要真正替人做 Gitea 上传/下载，不能依赖宿主机凭据管理器
  （换机器、换用户、容器化都会失效）。代价是威胁模型变化：**vault 泄露 = Gitea 全权限**，因此必须配合

     保存后**永不回显明文**，只显示「已配置（尾号 xxxx）」；提供「清除 Token」按钮。
     日志、审计、`/skill` 响应、`/api/profiles` 一律不得出现 token。
  2. **身份连通性检测（只测这一件事）**：点「检测」调一次 `GET /api/v1/user`，
     - 成功 → 「连接成功：<login>」，附带是否站点管理员（一行字）；
     - 失败 → 「连接失败：401 凭据无效 / 404 地址不对 / 超时」。
     **不探测仓库权限、不探测 package 权限、不做写探测**。
     理由（用户 2026-10-29 明确）：token 是人手工在 Gitea 里生成的，勾了哪些权限本人清楚，
     产品再去逐项推断，既不准（见下条）也没必要，反而制造「检测通过了 = 权限够用」的假安全感。
  3. **Gitea 不暴露 token scope**：实测 `/api/v1/user/tokens` 返回 404，
     `/api/v1/user/applications/oauth2` 只列 OAuth 应用，没有任何接口能查 PAT 自身的 scope。
     所以就算硬做权限表，结果也只能是「按账号角色推断」，不是「token 真实权限」——
     这正是本需求把它砍掉的原因，记录下来避免以后有人再想加。
  4. **不提供写权限探测**：任何会产生副作用（真实写入、创建、删除）的探测都不做。
     想验证能不能 push，直接去 push 一次，比在设置页里假装测一遍更可信。
  5. 与 REQ-107 的关系：本需求是 REQ-107 的前置条件 —— 没有入库的 token，守护进程无法代 Agent 做 Git 操作。
- 验收：填入错误 token 点检测 → 3 秒内显示「连接失败：401」；填入有效 token → 显示「连接成功：<login>」，
  且**不出现**任何仓库/package 权限结论；保存后刷新页面看不到明文；审计日志中搜索不到 token 原文。

### REQ-149 拦截策略统一架构：403 / 428 是同一张表的两级闸门

- 优先级：P1
- 状态：已实现·待联调（1.3.4）
- 背景：设置页原来是「灵魂三问」和「敏感权限自动屏蔽」两张并列的卡，用户看不出它们是**同一条
  流水线上的先后两道闸**，以为在配置两套互不相干的系统；「添加规则」只挂在后一张卡上，想加一条
  会触发灵魂三问的规则，得先跑到「屏蔽」卡里点按钮，再去下拉框里改层——动作与心智模型对不上。

- 需求（信息架构）：
  1. **一张卡、两个分组**。设置页只保留一张「拦截策略」卡，卡头右侧是唯一的「+ 添加规则」。
     卡内按等级分成两组，每组有自己的小标题与一句说明，顺序即执行顺序：
     `403 直接拦截` →（`428 灵魂三问`）→（`审批台`）。
  2. **卡头画一条流水线**：`403 直接拦截 → 428 灵魂三问 → 审批台`，三个徽标连成一排，
     直接说明「Agent 发来的每条命令都走同一条路」，两个等级不再是两套系统。
  3. **添加时显式选等级**，不再靠「在哪张卡点按钮」隐式决定；下拉框只有两项：
     `428 灵魂三问（Agent 自审后推审批）` / `403 直接拦截（不弹审批）`，
     默认 **428**，下方一行灰字「拿不准就选 428：先自审再让你决定，仍可拒绝；403 连『同意』都不给」。
  4. **跨级移动沿用同一个动作**：403 组内的规则给「降到 428」，428 组内的规则给「升到 403」，
     措辞用方向词而不是「移到屏蔽 / 移到三问」，因为后者读起来像两个平行仓库。
  5. 术语固定：**403 = 直接拦截（不弹审批）**、**428 = 灵魂三问（自审 + 审批）**。
     代码里的 `blocked` / `dangerous` 不再出现在界面上。
  6. 搜索框保留（`#secRuleSearch`），同时过滤两个分组；搜索框本身的视觉优化归 REQ-202。

- 设计取舍：
  - **为什么 403 不给审批选项**：看不懂的命令不该占用主人一次人工判断；给了「同意」按钮，
    就等于给人一个在疲惫时必然被点下去的按钮。403 的语义是「不讨论」。
  - **为什么新建默认 428**：误配成本不对称。配错成 403，正常操作被硬拦且 Agent 无法自愈
    （它连申请都发不出来）；配错成 428，最多多弹一次审批，主人点拒绝即可，代价可逆。
  - **为什么不做第三组「不拦」**：不拦＝把规则删掉，多一个「关掉但留着」的状态只会让人分不清
    「这条到底还在不在管」。

- 数据与接口：`rules.json` 三层（`blocked` / `dangerous` / `interactive`）**不变**，
  `interactive` 是内置的「每次都要三问且不可关」层，不出现在 UI 上。因此本次是纯前端重组 +
  文案统一，无数据迁移、无接口变更。

- 验收：设置页只有一张「拦截策略」卡；两组小标题与流水线可见；添加规则默认 428、可选 403；
  新增的 403 规则立即出现在 403 组；升降级按钮双向可用；搜索同时命中两组。

### REQ-150 会话关页即退 + 在线判定 + 记录折叠

- 优先级：P1
- 状态：已实现·待联调（1.3.4）
- 问题（真机联调暴露）：
  1. 关掉标签页后会话仍显示「在线」，最久要等 15 分钟（勾选档 4 小时）才消失；
  2. 同一浏览器先按域名登录、再按 IP 登录，会话列表里出现两条，看起来像「重复登录」；
  3. 「近期记录」常驻展开，占掉半屏。

- 根因（必须先说清，否则会继续当成 bug 追）：
  - 浏览器**不会**在关闭标签页时通知服务端。服务端唯一能观测到的信号是「还有没有请求」。
    所以「立即失效」在协议层做不到，能做的只有「尽快判定它已经不在了」。
  - 会话 cookie 的生命周期是**浏览器进程**，不是一个窗口/标签页。关标签页但浏览器进程还在，
    cookie 就还在，重新打开同一个地址仍是登录态；只有退出整个浏览器才会丢。
  - 域名与 IP 是**两个 origin**，cookie 按 origin 隔离，服务端拿到的是两条互不相干的 cookie，
    于是变成两条会话。这是浏览器安全模型，服务端无法合并，只能在列表里标注清楚。

- 方案：
  1. **关页即退（尽力而为）**：前端在 `pagehide` 时 `navigator.sendBeacon('/api/session/bye')`
     打一个标记，服务端**不立刻删**——刷新、站内跳转会马上发新请求，任何请求都撤销标记；
     超过 `SESSION_BYE_GRACE`（默认 60 秒）仍没有任何请求，才判定窗口真的关了，
     清掉会话并落审计 `session_bye`（与 `session_expired` 分开，否则分不清「我关的」和「自己掉的」）。
     宽限取 60 秒：主人要求「关掉窗口 1 分钟内就踢下线」。Chrome 对后台标签页的定时器
     最狠节流到 1 次/分钟，理论上贴着边界，但 `current()` 对正在发请求的那个会话带 `keep`，
     绝不会被自己的请求清掉；只有「另一个会话抢在它下一次心跳之前扫到」才会误踢，
     概率极低且重新登录即可，真被误踢可把 `AGENTKEYGUARD_SESSION_BYE_GRACE` 调回 120。
  2. **两个时间戳分工**：`last` = 最近一次真实活动（remember 续期或 touch），用于展示「最近活动」；
     `seen` = 最近一次任何请求（含 3 秒轮询），用于在线判定与超限淘汰。
     只看 `last` 会把挂着的标签页误报成离线，只看 `seen` 会把刚关掉的标签页显示成在线 90 秒。
  3. **在线判定**：`now - seen ≤ SESSION_ONLINE`（默认 90 秒）才算在线，否则标注「已离线」并置灰。
     会话计数改为「N 在线（· 共 M 条）」，不再把僵尸会话算进在线数。
  4. **一键清理**：卡头「清理已离线」调 `POST /api/sessions/prune`，只清 `seen` 已超期的记录，
     不含当前会话，落审计 `session_prune`。
  5. **近期记录默认折叠**：改用原生 `<details>`（默认收起，标题带条数），点开才展开。

- 边界与承诺：
  - 界面文案**不得**宣称「关窗立即失效」。准确说法是「关掉窗口约 1 分钟后记录消失；
    退出浏览器即需要重新登录」。
  - `pagehide` + `sendBeacon` 是尽力而为：浏览器崩溃、断电、进程被强杀都不会发出来，
    这种情况靠所在档位的 idle 兜底（15 分钟 / 4 小时）。
  - 同一浏览器的域名会话与 IP 会话会各自独立存在，靠设备摘要 + 来源 IP 区分，不做合并。

- 验收：开两个标签页 → 关掉一个 → 约 1 分钟后列表只剩一条；刷新页面不会把自己踢下线；
  `seen` 落后的会话显示「已离线」且可一键清理；近期记录默认收起。

### REQ-151 完成页不再回显 TOTP 密钥

- 优先级：P1
- 状态：已实现·待联调（1.3.6）
- 问题：初始化完成页最上面那块「TOTP 密钥」是一串 32 位 Base32 明文，长相和「首个接入链接」

- 判定：同一屏出现两种「看起来都像密钥」的东西，用户必然分不清哪个才是给 Agent 用的。
  给 AI 的入口只能有一个。
- 方案：
  1. 完成页删除 TOTP 密钥整块，只保留 主密码（默认掩码 + 眼睛）/ 访问地址 /

  接受这个取舍，理由：Step 2 是必过步骤，二维码与手动密钥当时就在屏幕上；

- 后续（未做，记在此）：设置页目前没有「重新绑定动态码」入口，真要换手机只能清库重装。
  若主人提出，按「主密码 + 当前动态码双重确认 → 生成新 secret → 校验新码 → 写 vault」实现。
- 验收：完成页看不到 32 位 TOTP 串；`/api/setup/finish` 响应里没有 `totp_secret`；

### REQ-152 会话收敛为两态：双档滑动计时 + 保持登录 + 状态条 + 会话卡

- 优先级：P1
- 状态：已实现·待联调（1.3.3）
- 问题：
  1. 原来「会话 1 小时绝对过期」，加上「锁定」「退出」「超时」三种说法，用户既分不清，也不知道多久掉线；
  2. 面板停在副屏等 AI 跑长任务时会莫名掉线，重登还要再输一次动态码；
  3. 会话看不见、踢不掉，关掉窗口后记录还挂着（后者由 REQ-150 收尾）。

- 方案（一句话：两个滑动计时取代绝对过期，选择只在登录时出现一次）：
  1. 登录页加「本窗口保持登录」勾选框，**默认不勾**。不勾 = 停手 15 分钟退出（`SESSION_IDLE`），
     勾选 = 4 小时兜底（`SESSION_IDLE_KEEP`）。**取消绝对过期上限**，`expires` 整条链删除，只留 `idle`。
  2. 续期分两路：勾选档任何请求都续期（含 3 秒轮询）；不勾档只认 `POST /api/session/touch`
     （`pointerdown` / `keydown` / `wheel`，60 秒节流）。Agent 伪造不到：touch 要会话 + CSRF。
     刻意**不在** `approval.ask_approval()` 里续期，否则 Agent 每秒发一个必被拒的请求就能把超时废掉。
  3. cookie 恒为会话级：`_cookie()` 不拼 `Max-Age`，`akg_session` 关浏览器即被丢弃；
     `Secure` / `HttpOnly` / `SameSite=Strict` / `Path=/` 全部保留。
  4. 面板底部常驻会话状态条（28px）：勾选档绿点「保持登录中，关闭窗口即退出」；普通档秒级倒计时，
     ≤60 秒转警示色，归零直接跳登录页（不等下一次 401）；每次轮询用服务端 `idle_in` 校准。
  5. 设置页「登录会话」卡：设备摘要 / IP / 登录时间 / 最近活动 / 是否保持登录 / 是否当前会话；
     非当前会话可「踢下线」（行内二次确认）；踢自己时服务端同时清 cookie，否则跳 `/login` 会被 302 弹回来。
  6. 「锁定」并入「退出登录」：新增 `POST /api/logout`，`/api/lock` 保留别名（自检 `[50]` 与旧脚本不受影响）；
     顶栏与设置页文案统一。`423 vault_locked` 是「保险库尚未解密」，与登录态无关，语义一律不动。

- 取舍：
  - 勾选档给 4 小时而不是 15 分钟：主人会把面板挂在副屏等 AI 跑 1–2 小时，浏览器回收闲置标签页或
    系统短暂睡眠都会让 15 分钟档掉线；4 小时覆盖「看部电影 + 合盖一次」。
  - 放宽不削弱安全：cookie 是会话级，关窗即被浏览器丢弃，服务端那条记录**无法被任何请求命中**；
    它只是内存里的 dict，`SESSION_MAX = 8` 会自然淘汰。真正兜住「关窗即退」的是 cookie 生命周期。
  - 明确边界：Chrome「继续上次会话」会恢复会话 cookie，此时靠所在档位兜底；
    文档与登录页**不得**宣称「绝对瞬时失效」。

- 验收：不勾选停手 15 分钟跳登录页；勾选后挂 1 小时仍在；关浏览器再开必须重新登录；
  状态条倒计时与服务端 `idle_in` 一致；踢下线后对方下一次请求即跳登录页；退出登录后 `/api/me` 401。

### REQ-303 mTLS 双向认证

- 优先级：不做
- 状态：不做
- 需求：不启用 mTLS，不签发客户端证书（p12 / mobileconfig 设备描述文件），不在 TLS 握手时索要客户端证书。
- 理由：
  1. **威胁模型不匹配**。本项目的唯一目标是不让云端 LLM 看到凭证明文，防护边界在"AI ↔ 守护进程"之间，与"哪台设备能连服务"无关。设备身份由主密码 + TOTP + IP 白名单 + 会话共同保证，已经够用。
  2. **代价高、收益低**。mTLS 要求每台设备单独签发并安装客户端证书，手机换机、系统重装都要重签；家庭内网没有设备生命周期管理。
  3. **负体验**。2026-10-29 联调实测：只要服务端在握手时索要客户端证书，Windows 就会弹出「选择用于身份验证的证书」，列出系统里所有企业证书与手机证书；选错一张直接握手失败。用户无从判断该选哪个。
- 处理：`devices.py`、`/api/devices*`、`bootstrap_context` 中的客户端证书相关代码在 v1.1.2 一并清理，`tls_context()` 固定 `CERT_NONE`（见 REQ-113）。

### REQ-305 模型 API Key / 模型网关

- 优先级：不做
- 状态：不做（2026-10-31 定稿）
- 需求：不在 AKG 内管理模型 API Key，也不把 AKG 做成模型网关。
- 理由：
  1. **生命周期冲突**。SSH / 数据库 / Git 凭证以年为单位稳定；模型 Key 按周甚至按天变
     （供应商换、版本迭代）。AKG 的「凭证 = 长期身份」假设在这里不成立。
  2. **调用频率冲突**。AI 操作其他模型是高频行为，一次对话可能几十上百次调用；
     逐次审批不可用，而一旦不审批，AKG 就退化成「存 key 的地方」，失去存在意义。
  3. **已有成熟方案**。New API / one-api / LiteLLM 专门解决多供应商聚合、模型白名单、
     配额与计费。再在 AKG 里做一遍等于重复造轮子，且做得更差。
  4. **字段边界划不清**。截图里「添加模型」那套表单（模型名、工具调用、图片输入、
     输入输出长度）属于**调用参数**而非身份，固化进凭证会导致「换个模型就要改凭证」，
     正是 REQ-107 刚从 git 凭证上拆掉的东西。
- 替代做法：模型权限在网关侧配置（哪些模型可访问、配额多少）；网关给下游发的 token
  属于「可下发的密钥」，用现有的**服务静态注入**（`AGENTKEYGUARD_ENV_URL`）注入环境变量，
  不新增凭证类型。
- 若将来确有需要：新增类型必须同时打通 `/skill` 输出、调用示例、审批卡片、自检断言一整套，
  且要先解决 SSE 流式转发、60 秒级超时、计费失控三个工程问题——这三件都不是 AKG 擅长的事。

- `python3 -m compileall agentkeyguard` 无输出；`PYTHONPATH=. python3 -m agentkeyguard selftest` 末行「全部通过。」；
